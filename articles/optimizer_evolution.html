THE PROBLEM
Why Optimizers Matter OVERVIEW
Training a neural network means finding the set of parameters (weights) that minimize a loss function. The loss function is a high-dimensional surface — a landscape with valleys, ridges, saddle points, and flat plateaus. An optimizer is the algorithm that navigates this landscape, deciding how to update each parameter at every training step. The choice of optimizer profoundly affects training speed, stability, and final model quality.

Evolution of optimizers — each solves the previous one's problems
🎯
The fundamental question

Given a gradient ∇L (the direction of steepest ascent), how should we update parameters? Vanilla gradient descent says: go in the opposite direction by a fixed step size. But real loss landscapes are complex — they have narrow ravines where one direction is much steeper than another, saddle points where gradients vanish, and noisy gradients from mini-batch sampling. Each optimizer in this article addresses specific failure modes of its predecessor.

The evolution chain: SGD → SGD+Momentum → AdaGrad → RMSprop → Adam → AdamW → Muon. Each step introduces a key insight: momentum accumulates gradient history, adaptive methods scale per-parameter, Adam combines both, AdamW fixes weight decay, and Muon leverages second-order structure.
STOCHASTIC GRADIENT DESCENT
SGD — The Foundation FIRST-ORDER
Stochastic Gradient Descent is the simplest optimizer. At each step, it computes the gradient of the loss on a mini-batch of data (not the full dataset — that's what makes it "stochastic") and updates parameters in the opposite direction. The update rule is beautifully simple: θ = θ - η · ∇L, where η is the learning rate. But this simplicity comes with severe limitations that motivated decades of optimizer research.
θt+1 = θt - η · ∇L(θt)

Problem 1 — Noisy zig-zagging: Because each mini-batch gives a slightly different gradient estimate, SGD's path zig-zags erratically instead of moving smoothly toward the minimum. On elongated loss surfaces (common in deep learning), the gradient points mostly across the narrow direction, causing wild oscillations perpendicular to the valley while making tiny progress along it.
Problem 2 — One learning rate for all: SGD uses a single learning rate η for every parameter. But different parameters may need very different step sizes — parameters connected to frequently-activated features get large gradients and may overshoot, while parameters for rare features get tiny gradients and barely move. There's no way to tune η to satisfy both.
Problem 3 — Saddle points: In high-dimensional spaces, saddle points (where the gradient is near zero but it's not a minimum) are far more common than local minima. SGD slows to a crawl near saddle points because the gradient signal becomes vanishingly small, and with noisy mini-batch gradients, the optimizer can get stuck oscillating around the saddle for many iterations.
Problem 4 — Ravines: A ravine is a region where the loss surface curves sharply in one direction but gently in another. The gradient at any point in a ravine points mostly across the ravine (the steep direction), not along it (toward the minimum). SGD bounces back and forth across the narrow direction, making painfully slow progress toward the optimum.
What SGD gets right: Despite its problems, SGD has a powerful implicit regularization effect — the noise from mini-batch sampling actually helps generalization by preventing the optimizer from overfitting to sharp, narrow minima. This is why SGD+Momentum remains competitive with Adam for many tasks, especially in computer vision.
MOMENTUM
SGD + Momentum — Building Velocity MOMENTUM
The key insight of momentum: accumulate a running average of past gradients and use that to update parameters instead of just the current gradient. Think of a ball rolling down a hill — it builds up speed in consistent directions and dampens oscillations. The velocity vector v accumulates gradient history, so if gradients consistently point the same way, momentum accelerates; if they flip-flop (zig-zagging), momentum dampens them.
vt = β · vt-1 + ∇L(θt)
θt+1 = θt - η · vt

How momentum fixes zig-zagging: In a ravine, gradients across the narrow direction flip sign each step. Momentum averages these out — the oscillations cancel while the consistent component along the valley accumulates. The result: faster progress along the valley with reduced bouncing. With β=0.9, the effective step in the consistent direction is ~10x larger than a single gradient step.
⚽
The rolling ball analogy

Imagine a ball rolling down a bumpy hill. Without momentum (vanilla SGD), the ball teleports at each step — no memory of where it was going. With momentum, the ball has inertia. It accelerates down smooth slopes, powers through small bumps, and only slowly changes direction when the terrain truly changes. The momentum coefficient β controls how "heavy" the ball is — higher β means more inertia, smoother trajectory, but slower to respond to gradient changes.

Remaining problem 1 — Still one learning rate: Momentum smooths the trajectory but still applies the same learning rate to every parameter. A parameter that only activates for rare inputs still gets the same η as one that fires on every sample. This is especially problematic in NLP where word embeddings for rare words receive very sparse gradient updates.
Remaining problem 2 — No per-parameter adaptation: Momentum treats all dimensions equally. If the loss surface is elongated differently in different parameter dimensions, momentum can't adapt — it applies the same β and η everywhere. What we really need is a way to automatically scale the learning rate per parameter based on the gradient history for that specific parameter.
ADAPTIVE LEARNING RATES
AdaGrad → RMSprop ADAPTIVE
The next breakthrough came from a completely different direction: instead of smoothing gradients (momentum), what if we adapt the learning rate for each parameter individually? AdaGrad (2011) introduced this idea by accumulating squared gradients — parameters with large historical gradients get smaller learning rates, and parameters with small gradients get larger ones. But AdaGrad had a fatal flaw that RMSprop (2012) elegantly fixed.
AdaGrad accumulates the sum of all squared gradients since the start of training. This sum only grows, so the learning rate monotonically decreases. For convex problems, this is actually optimal. But for deep learning's non-convex landscapes, training may need to increase the learning rate when entering new regions — and AdaGrad can't do this. After many steps, the accumulated sum becomes so large that the effective learning rate approaches zero and training stops prematurely.
AdaGrad: Gt = Gt-1 + gt²   →   θt+1 = θt - (η / √(Gt + ε)) · gt
RMSprop (Hinton, 2012) fixes this with one simple change: use an exponential moving average of squared gradients instead of the cumulative sum. This means old gradient information gradually decays, so the effective learning rate can both increase and decrease. The optimizer "forgets" ancient gradient history and adapts to the current region of the loss surface.
RMSprop: E[g²]t = β · E[g²]t-1 + (1-β) · gt²   →   θt+1 = θt - (η / √(E[g²]t + ε)) · gt

How RMSprop adapts per-parameter: Consider two parameters: one with consistently large gradients (say, a bias term in a frequently-used layer) and one with small, sparse gradients (an embedding for a rare word). RMSprop divides each gradient by √(E[g²]) — for the large-gradient parameter, this denominator is large, shrinking its effective step. For the small-gradient parameter, the denominator is small, enlarging its step. Each parameter automatically gets an appropriate learning rate.
🔑
Why exponential moving average is the key insight

The difference between AdaGrad and RMSprop is the difference between memory and attention. AdaGrad remembers every gradient forever (sum), so parameters that were active early in training are permanently penalized. RMSprop pays attention to recent gradients (exponential decay), so if a parameter enters a new region of the loss surface, its effective learning rate can adapt. With β=0.9, gradients from ~10 steps ago contribute only ~35% as much as the current gradient. Gradients from ~50 steps ago contribute less than 1%.

Remaining problem 1 — No momentum: RMSprop adapts learning rates per-parameter but has no momentum — it doesn't smooth out noisy gradient directions. The trajectory is still subject to the noise of individual mini-batches. Can we combine the benefits of momentum (smooth direction) with adaptive rates (per-parameter scaling)?
Remaining problem 2 — Bias at initialization: The exponential moving average E[g²] is initialized to 0. In the first few steps, the estimate is heavily biased toward zero, leading to artificially large initial updates. This can cause instability at the start of training.
ADAPTIVE MOMENT ESTIMATION
Adam — Best of Both Worlds ADAM
Adam (Kingma & Ba, 2015) combines the two key ideas: momentum (first moment — running average of gradients, like SGD+Momentum) and adaptive learning rates (second moment — running average of squared gradients, like RMSprop). It also introduces bias correction to fix the initialization problem. Adam became the default optimizer for most deep learning tasks because it "just works" with minimal hyperparameter tuning.
mt = β₁ · mt-1 + (1-β₁) · gt     (1st moment — momentum)
vt = β₂ · vt-1 + (1-β₂) · gt²     (2nd moment — adaptive rate)
m̂t = mt / (1 - β₁t)     (bias correction)
v̂t = vt / (1 - β₂t)     (bias correction)
θt+1 = θt - η · m̂t / (√v̂t + ε)

💡
Why bias correction matters

Both m and v are initialized to 0. In the first step with β₁=0.9: m₁ = 0.1·g₁ (only 10% of the gradient!). The bias-corrected version: m̂₁ = m₁/(1-0.9¹) = m₁/0.1 = g₁ (the full gradient). Without correction, the first ~10 steps would use severely underestimated gradients and squared gradients, causing either sluggish starts or unstable behavior. As t grows, (1-β^t) → 1 and the correction vanishes — it's only needed for the first few steps.

Why Adam "just works": The first moment (momentum) smooths noisy gradients, giving a better estimate of the true gradient direction. The second moment (adaptive rate) normalizes each parameter's update by its recent gradient magnitude. Together, they produce updates that are both well-directed and well-scaled. Default hyperparameters (β₁=0.9, β₂=0.999, η=0.001) work surprisingly well across many architectures and tasks.
Problem — Weight decay is broken in Adam: When you add L2 regularization to Adam (adding λ·θ to the gradient), something subtle goes wrong. The L2 penalty gradient (λ·θ) gets divided by √v̂ just like the task gradient. But the adaptive scaling that helps the task gradient hurts the regularization — parameters with large gradients get less regularization than intended. This means Adam's L2 regularization is not equivalent to true weight decay, leading to worse generalization than SGD+Momentum on many tasks.
Problem — Generalization gap: Despite converging faster, Adam often finds solutions that generalize worse than SGD+Momentum. This "generalization gap" was a major concern in computer vision tasks. The root cause is partially the weight decay issue (fixed by AdamW) and partially that Adam's adaptive rates reduce the beneficial noise that helps SGD escape sharp minima.
DECOUPLED WEIGHT DECAY
AdamW — Fixing Regularization ADAMW
Loshchilov & Hutter (2019) identified the core problem: in SGD, L2 regularization and weight decay are mathematically equivalent. But in Adam, they are not! When you add an L2 penalty (λ·θ²/2) to the loss, the gradient becomes g + λ·θ. Adam divides this entire gradient by √v̂, so the regularization term λ·θ also gets scaled by the adaptive learning rate — parameters with large past gradients receive less regularization. AdamW fixes this by applying weight decay directly to the parameters, completely separate from the gradient-based update.
Adam + L2 (broken)
● Gradient: gt = ∇L + λ·θ
● m, v computed on (∇L + λ·θ)
● Update: θ -= η · m̂ / √v̂
● Regularization scaled by 1/√v̂
● Large-gradient params: less decay
● Small-gradient params: more decay
AdamW (correct)
● Gradient: gt = ∇L  (no λ·θ!)
● m, v computed on ∇L only
● Adaptive update: θ -= η · m̂ / √v̂
● Weight decay: θ -= η · λ · θ
● All params: same decay rate λ
● Regularization independent of v̂
AdamW: θt+1 = θt - η · (m̂t / (√v̂t + ε) + λ · θt)
Adam + L2 vs AdamW — how adaptive rates distort regularization
🔬
Why this matters for generalization

Weight decay pushes all parameters toward zero, preventing the network from relying too heavily on any single parameter. In Adam+L2, parameters with large gradients (which already have large v̂) receive reduced regularization — exactly the parameters that might benefit most from it. AdamW ensures uniform regularization: every parameter decays by the same fraction λ per step, regardless of its gradient history. This simple fix closes much of the generalization gap between Adam and SGD+Momentum.

AdamW is now the standard: Nearly all modern large language models (GPT, LLaMA, etc.), vision transformers, and diffusion models use AdamW as their optimizer. PyTorch made AdamW a separate optimizer class (torch.optim.AdamW) specifically because this distinction matters. If you're using Adam with weight_decay > 0 in the old Adam class, you're doing it wrong — switch to AdamW.
Remaining problem 1 — First-order only: AdamW still only uses gradient information (first derivative). It has no knowledge of the loss surface's curvature (second derivative / Hessian). A second-order optimizer could take larger steps in flat directions and smaller steps in curved directions, converging much faster. But computing the full Hessian is O(n²) in parameters — prohibitively expensive for modern networks with billions of parameters.
Remaining problem 2 — Per-parameter independence: AdamW scales each parameter independently. It doesn't consider relationships between parameters — how the loss changes when two parameters change together. The optimal update for one parameter depends on what all other parameters are doing, but AdamW ignores this cross-parameter structure entirely.
MOMENTUM + ORTHOGONALIZATION
Muon — Cheap Second-Order Updates MUON
Muon (Momentum + Orthogonalization + Newton, Jordan et al. 2024) takes a fundamentally different approach. Instead of tracking per-parameter statistics like Adam, Muon orthogonalizes the momentum buffer using Newton-Schulz iterations — a cheap approximation to multiplying by the inverse square root of the gradient covariance matrix (GTG)-1/2. This gives the optimizer awareness of cross-parameter correlations and implicitly incorporates second-order curvature information, achieving near-second-order convergence at first-order computational cost.
The core idea: after computing Nesterov momentum (a look-ahead version of momentum), Muon orthogonalizes the update matrix by projecting it onto the Stiefel manifold (the set of matrices with orthonormal rows/columns). This is done via Newton-Schulz iterations — a simple iterative formula that converges to the polar decomposition X·(XTX)-1/2 without ever computing the inverse explicitly. The orthogonalized update has several remarkable properties:
Muon algorithm — Nesterov momentum + orthogonalization
Why orthogonalization helps
● Equalizes singular values of update
● Large gradient directions: scaled down
● Small gradient directions: scaled up
● All directions get equal "energy"
● Approximates natural gradient
Newton-Schulz iteration
● Initialize: X₀ = G / ‖G‖F
● Iterate: Xk+1 = aXk + bXk(XkTXk) + c(XkTXk)Xk
● 5 iterations suffice (fast convergence)
● Only matrix multiplications — GPU-friendly
● Result: orthogonal update matrix

⚡
The spectral perspective

Think of the gradient matrix G as having multiple "directions" with different magnitudes (singular values). AdamW scales each parameter independently but doesn't change the relative directions. Muon's orthogonalization sets all singular values to 1, making the update uniformly energetic in all directions. This is equivalent to preconditioning by (GTG)-1/2 — a form of natural gradient descent that accounts for the geometry of the parameter space. It's like having a perfectly conditioned Hessian approximation for free.

When to use Muon: Muon is designed for matrix-shaped parameters (weight matrices in linear layers, attention projections, etc.) — which make up the vast majority of parameters in transformers. For embeddings and 1D parameters (biases, norms), AdamW is still used alongside Muon. In practice, Muon achieves comparable or better results to AdamW with significantly fewer training steps, especially for large language models.
Computational cost: The Newton-Schulz iterations add ~5 matrix multiplications per optimizer step. For large models this is a small fraction of the forward/backward pass cost. Muon's overhead is minimal compared to its convergence speedup — often reaching the same loss in 2x fewer steps.

SUMMARY
Key Takeaways SUMMARY
Each optimizer in the evolution chain was born from a specific limitation of its predecessor. Understanding why each was invented is more important than memorizing the update rules — it reveals the fundamental challenges of navigating high-dimensional loss landscapes.
The complete evolution — problems and solutions
📊
Key takeaways

SGD: Simple but zig-zags, one learning rate for all. Momentum: Smooths trajectory via velocity accumulation. AdaGrad: Per-parameter rates but learning rate dies. RMSprop: Fixes AdaGrad with exponential decay. Adam: Combines momentum + adaptive rates + bias correction. AdamW: Fixes broken weight decay for better generalization. Muon: Cheap second-order via orthogonalization — aware of cross-parameter structure.

Practical advice: For most tasks, start with AdamW (β₁=0.9, β₂=0.999, lr=3e-4, weight_decay=0.01). For large language models and where compute is critical, consider Muon for matrix parameters with AdamW for embeddings. SGD+Momentum remains excellent for computer vision tasks with careful learning rate scheduling. The "best" optimizer depends on your task, model, and compute budget.
